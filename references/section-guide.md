# 各章节写作细则

按 `SKILL.md` 的强制结构逐章展开。每节给「必须写什么 / 怎么算合格 / 反例」。

---

## 1 结论

**必须写什么**

1. 开头 2~3 句：这次一共几件事、彼此是否相关、是不是并行做的。
2. 一张「事项 / 真实原因 / 状态」三列表。原因列要写成 **「不是 X，而是 Y」** 的句式，
   因为读者最想知道的是你排除了什么。
3. 4~5 个 KPI 卡片，每个都带对比（改前 → 改后）或口径（采样次数、单位）。
4. 一行小字说明数据来源与单位。

**合格标准**：只读这一章，能知道「哪件事好了、哪件还没好、好在多少」。

**反例**

- ✗「经过排查，问题已基本解决」——没说是哪件、解决到什么程度。
- ✗ KPI 只写「19.8 ms」，不写「从 43.3 ms 降下来」——读者不知道这是好还是坏。
- ✗ 在结论里展开技术细节，把 3~5 章的内容重复一遍。

**状态三档的用法**

| 档位 | 含义 | 典型措辞 |
|---|---|---|
| 已闭环 | 改完并回读验证，有实测数据 | `已修复`、`已验证` |
| 部分闭环 | 关键动作做了，但还有一步受权限/环境阻断 | `部分闭环`、`2 项已改，1 项待提权` |
| 未闭环 | 只完成了定位，没动 | `待办`、`仍是嫌疑` |

## 2 验收判据

**表格四列**：项目 / 判据 / 实测 / 结论。数字列加 `class="n"` 右对齐。

**判据列的要求**：必须可量化或可判定。`< 5 ms`、`= 0`、`State=Disabled`、`完全一致` 都行；
「良好」「正常」不行。

**必须有 FAIL 行。** 一份全是 PASS 的验收表通常意味着判据定得太松。
今天的报告里 `禁用 360 更新任务 → 拒绝访问 → FAIL（待提权）`，
这一行恰恰是报告可信度的来源。

**要包含排除性判据。** 例如「全屏弹出：排除显示链路 / 判据：非黑屏型 / 实测：完整桌面，需点任务栏 / PASS（排除）」。
排除也是结论，值得单列一行。

## 3…N 具体项目

**章节标题用现象，不用结论。**

- ✓ `3 故障一：LOL 全屏被弹出`
- ✗ `3 360 更新器抢焦点导致弹出`

因为标题一旦写出结论，读者会跳过推理直接接受——包括你自己下次也会。

### 3.1 现象与分流

**三步**：

1. 抄用户的原话（关键，它往往自带排除信息）。
2. 说明这句话能排除掉哪几种可能。
3. 给一张「可能机制 / 判别特征 / 判定」三列表。

用户说「弹出后什么都没有」——这一句就排除了「广告弹窗被拦截」（会留痕），
指向「空壳窗口」或「显示重连」。用户又说「必须点任务栏才能回来」——
排除了黑屏型，锁定为「窗口被最小化」。

**分流表是这一节的核心产出**，它把模糊描述变成可判定的分支。

### 3.2 证据

放实测数据、扫描结果、日志片段。要求：

- 数据可复现（附命令，或指向 8.2）
- 解释数据为什么指向这个原因，不能只贴表
- 相互矛盾的数就都列出来，并解释差异（例：解析值 10.6 V vs 实测 12.03 V，差 13 % 是因为假设不成立）

### 3.3 处置

**写清三件事**：改了什么、为什么这样改、改之前做了什么预防动作。

预防动作最容易被省略，但它往往是整段最有价值的部分。例：

> 改 `config.json` 前必须先 `Stop-Process` 结束 `wallpaper32` 与 `wallpaperui`，
> 否则应用退出时会用内存中的旧设置覆写回文件。

用 `.eq` 块展示「改前 → 改后 + 备份路径」，一行一个变更，方便核对。

### 3.4 结果

分「已生效 / 未闭环 / 待办」三档写。有回读就写回读值，不要只说「已修改」。

## 多轮增量怎么整合

一轮验收反馈又产生了新任务？把它们**插进 `3…N` 并整体重排**，而不是在文末追加
「第 N+5 章」——`优化项 / 已知缺口 / 文件与复现 / 依赖与知识清单` 四章必须始终压轴，
且依赖与知识清单永远是最后一章。

1. **新任务章按轮次接在既有任务章后面**：原 3~7 是第一轮，新增 8~10 就是第二、三轮，
   每章沿用「现象 / 需求 → 处置 → 证据 → 结果」的小节结构。
2. **尾部四章顺延重编号**，标题、`id` 锚点、目录条目三者同步。
3. **同步更新的位置一个都不能漏**：
   - 结论：开头句补一句本轮增量；事项表追加一行；KPI 数字改成最终值；
   - 验收判据：新判据追加在表尾；过程中真实出现过的 FAIL 保留 FAIL 行（这是可信度来源）；
   - 产物清单、复现命令、还原方法；
   - 依赖与知识清单：本轮新引入的库 / 技术补进表，版本回读后填实测值；
   - 全文「第 N 章」交叉引用——重排后全局 grep「第 N 章」逐条核对；
   - 目录（`add_toc.py` 对已有目录是跳过的，重排后必须手工同步 nav 条目与锚点）。
4. **每轮的用户原话保留在对应章节开头**——它自带排除信息，是下一轮分流的地基。
5. 读者验收时报告的错误，也要回流：修复写成 O 项；如果暴露的是当初验收方式的盲区
   （如测试顺序掩盖了缺陷），如实写进 O 项与判据，不要只改代码不提旧结论失准。

## N+1 优化项

**每条严格三段**：现象 → 定位与处置 → 结果。

| 段 | 必须包含 |
|---|---|
| 现象 | 具体数值或原始日志行，不要形容词 |
| 定位与处置 | 用什么手段找到的（命令 / 对照实验 / 排除法），改了什么，为什么 |
| 结果 | 已生效 / 未闭环 / 待办，附回读或验证方式 |

**数量**：3~10 条。少于 3 条说明复盘不够细；多于 10 条考虑合并同类项。

**标题要点明机制，不要复述现象。**

- ✓ `O2 壁纸引擎的 "pause" 不等于 "stop"`
- ✗ `O2 壁纸引擎设置有问题`

**反证必须单独成条**，标题前加 `【反证】`。格式同上，但第一段叫「假设」：

```
O9 【反证】蓝牙耳机不是 2.4 GHz 干扰源
假设：2.4G 与蓝牙共用频段，机器上配对了多副耳机，听起来很像干扰源。
验证：查音频端点，当前只有有源音箱与 HDMI，没有任何蓝牙音频端点。
结果：排除。剩下的干扰来自同频 AP 与 40 MHz 带宽本身。
```

一次排查排除了两个可疑对象，就值两条 O 项。反证的价值等于正证——
它防止下一个人重复走同一条死路。

**自测发现的缺陷也要写。** 今天工具首次实跑就把任务栏误判成「空壳弹窗」，
这条写成了 O11，比任何「工具已通过校验」的表述都诚实。

## N+2 已知缺口

**写「暂无」即不合格。** 任何一次工作都有缺口，找不到就是没找。三类去处：

| 类型 | 找法 |
|---|---|
| 未闭环 | 搜全文的「拒绝访问」「需要管理员」「需登录后台」 |
| 未验证 | 搜「校验通过但未实跑」「语法检查」「未在真实场景触发」 |
| 仍是嫌疑 | 搜「待观察」「高度吻合」「强嫌疑」 |

每条要写**为什么没做完 + 需要什么条件才能做**，不要只写「未完成」。

---

## N+3 文件与复现

三个子节：

1. **产物清单**：文件 / 类型 / 用途。路径要能直接找到（绝对路径或说明所在目录）。
2. **复现命令**：可直接粘贴执行，含变量定义，不要用 `...` 省略。
3. **还原方法**：改过的配置怎么退回去。这一节体现「可逆」，读者才敢照着做。

命令块用 `<pre>`，不要用行内 `code`——多行命令必须保留换行。

---

## N+4 依赖与知识清单

整份报告的最后一章，回答两个问题：接手的人要装什么；读不懂的人该补哪一块背景。

### 判型：只写一组

| 类型 | 判定标准 | 表头 |
|---|---|---|
| 代码类 | 产出了源码 / 脚本 / 页面，或改动过代码 | 库 / 类别 / 版本 / 在本项目里干什么 / 是否可去 |
| 其它类 | 排障、配置、运维、调研，无源码产出 | 技术 / 用在哪一步 / 作用 |

判错的典型后果：一次「排查 360 抢焦点」硬套库表，表里全是空行；或一个 Node 服务只写
「技术：Node.js」，读者仍不知道该 `npm i` 什么、要哪个大版本。

### 代码类：库表

只列四类，**标准库一律不列**（`os` / `sys` / `re` / `json` / `pathlib` / `subprocess` 不算依赖）：

| 类别 | 例 | 取版本的命令 |
|---|---|---|
| `Python 非标准库` | `requests`、`pdfkit`、`Pillow` | `pip show <pkg>` |
| `前端库·直接依赖` | 写进 `package.json` 的 `chart.js` | 读 `package.json`，`npm ci` 可完整还原 |
| `前端库·CDN` | `<script src="https://cdn…">` | 看 URL 里的版本号，断网即失效 |
| `CLI 工具` | `chrome`、`ffmpeg`、`accoreconsole` | `<tool> --version` |

「是否可去」列不是凑数：写「不可去，核心渲染全靠它」或「可去，只有一行格式化用到」，
下一个人才敢裁剪。版本列禁止填 `latest` 或照抄 README。

### 其它类：技术表

列「技术 / 用在哪一步 / 作用」。「用在哪一步」要能对回正文章号（`3.3 节`、`O5`），
不写「全局」；「作用」写它解决了什么约束，不写它是什么。

### 基础知识点（两类都写，不许写「无」）

找法：回到第 1 章结论，逐条问「读懂这句需要先知道什么」。每条三列：知识点 / 一句话定义
（≤ 30 字）/ 本报告哪里用到。

| 知识点 | 一句话定义 | 本报告哪里用到 |
|---|---|---|
| `position:fixed` 的包含块 | 祖先带 `transform` 时固定定位相对该祖先而非视口 | 8 章目录条错位 |
| 壁纸引擎 pause 的语义 | `pause` 只停渲染不停进程，退出时仍回写配置 | O2 |
| 控制台代码页与脚本编码 | 控制台按 OEM 代码页解码，脚本按 UTF-8 写就乱码 | 4.2 节乱码 |

不合格：`HTML 基础`、`Python 语法`、`网络知识`——读者不知道具体要补哪一段。
少于 2 条说明没站到读者角度。

## 图表规范

- 用**内联 SVG**，不引外部库（离线可看）。
- 每张图配一句 caption，**说明这张图证明了什么**，不是描述图里有什么。
  - ✓「红线在第 20 个采样点丢包后冲到 712 ms；蓝线全程贴合基线，最大 152 ms、零丢包。」
  - ✗「图 1 延迟曲线」
- 双序列对比时，两条线用不同色相（暖/冷），图例放空白角。
- Y 轴范围决定叙事：想让读者感受「尖峰有多离谱」就用线性到最大值；
  想让读者看清「基线差异」就放大到 0~60 ms。必要时两张都画。
- 丢包点在序列图里用 ✕ 标在基线处，别画成 0 ms（那是「很快」不是「没有」）。

画完**必须**跑 `scripts/check_svg.py`，再做无头 Chrome 目视。
几何自检能挡越界和重叠，挡不住「信息没画出来」，两者都要过。

## 排版约定

| 元素 | 用法 |
|---|---|
| `.kpi` | 4~5 个关键数字，放在第 1 章 |
| `.eq` | 改前→改后、公式、单行结论 |
| `.pass` / `.fail` / `.warn` | 绿 / 红 / 土黄，只用于状态判定 |
| `td.n` | 数字列右对齐 |
| `<small>` | 口径说明、数据来源、附注 |
| `code` | 命令、文件名、注册表键、进程名 |

数字与单位之间留半角空格（`19.8 ms`、`3.3 %`），中文与数字之间也留空格（`平均 19.8 ms`）。
